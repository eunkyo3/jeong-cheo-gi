## 감사 방법 (읽고 시작할 것)

1. **JSON 을 먼저 보지 않는다.** `sourceImages` 의 이미지와 `data/raw/<회차>/` 원본
   (`page.txt`, `article.html`, `imgNN`)만 보고 **독립적으로 재판독**한다.
2. 재판독이 끝난 뒤에야 `data/rounds/<회차>.json` 을 열어 대조한다.
3. 문항마다 아래 **판정 / 등급 / 근거** 3칸을 채운다. 빈칸이 남으면 감사 미완료다.

- `근거` — 무엇을 어디서 보고 그렇게 판단했는지(이미지 파일명, page.txt 줄 번호 등).

### 추가로 수행한 검사 (표본 밖)

이 회차는 고위험 문항이 4건뿐이라 실효 커버리지가 40%로 낮다. 표본이 놓칠 수 있는
구조적 위험을 두 가지 보강 검사로 덮었다.

1. **서술형 누락 검사 — 전 20문항 대상.** "서술하시오/설명하시오" 발문을 가진 문항과
   `keywords` validator 를 가진 문항을 교차 대조했다. 결과: #7, #14 두 건뿐이고 **둘 다
   validator 를 갖고 있으며 둘 다 감사 표본에 포함**되어 있다. 즉 서술형인데 strict 매칭으로
   남아 표본 밖에 숨은 문항은 없다. (이 검사를 한 이유: 서술형을 accept 열거로 처리하면
   고위험 분류에 잡히지 않아 표본에서 빠질 수 있는데, 그 경우 정상 답안이 대량 오답 처리된다.)

2. **keywords validator 동작 검증 — #7, #14 100%.** 정답 패러프레이즈 9종과 무관 문장 8종을
   실제 `gradeQuestion` 으로 채점했다. 결과 9/9 PASS, 8/8 FAIL 로 전건 기대와 일치.
   특히 #14 에서 "스크립트를 삽입하는 공격"(XSS 설명)이 any 키워드에 걸림에도
   all 의 "sql" 이 없어 FAIL 되는 것을 확인해, all/any 분리가 오탐 방지로 작동함을 검증했다.

### 특기 사항

- **#2** — 파이썬 set 의 비결정적 출력 순서를 accept 240건(120 순열 × 따옴표 2종) 열거로 해결했다.
  240건을 전수 파싱해 중복 0건, 전부 정확한 5원소 순열임을 확인했다. 규모가 큰 만큼
  누락·오타가 섞이기 쉬운 방식인데 실제로는 완전했다.
- **#19** — 코드가 `"a=" + a` 이므로 실제 출력은 공백 없는 `a=10` 이다.
  블로그 더보기 표기는 `a = 10` 인데 JSON 은 sampleAnswer 를 `a=10` 으로 두고 블로그 표기는
  관용 accept 로만 넣었다. keepSpace 문항이라 이 구분이 채점에 직접 영향을 준다.
  (2021-1 #17 에서도 동일한 판단이 적용되어 있어 회차 간 처리 일관성이 확인된다.)
