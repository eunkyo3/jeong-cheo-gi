>
> **이 감사는 표본 검사이며 완전 보증이 아니다.** 규약상 의무 범위는 무작위 표본 20%(최소 4문항)와
> 고위험 문항(validator / 다필드 / 코드 출력) 100% 이며, 그 밖의 문항에 남은 오류를 배제하지 않는다.
> 운영 중 "정답 이의 제기" 버튼이 상시 신고 경로다.

> 생성: `node scripts/audit-round.mjs 2024-1 --seed 366590647`
> 이 파일은 **빈 서식**이다. 생성기는 어떤 판정도 채우지 않는다.

## 감사 방법 (읽고 시작할 것)

1. **JSON 을 먼저 보지 않는다.** `sourceImages` 의 이미지와 `data/raw/<회차>/` 원본
   (`page.txt`, `article.html`, `imgNN`)만 보고 **독립적으로 재판독**한다.
2. 재판독이 끝난 뒤에야 `data/rounds/<회차>.json` 을 열어 대조한다.
3. 문항마다 아래 **판정 / 등급 / 근거** 3칸을 채운다. 빈칸이 남으면 감사 미완료다.

### 불일치 등급 (RESTORE_GUIDE "감사 규약")

| 등급 | 정의 | 조치 |
|---|---|---|
| **A급** | 채점 영향 또는 지문 내용 변경 — `bodyHtml`/`bodyText` 의 수치·식별자·코드 리터럴·표 셀 값, `accept`·`validator`·`sampleAnswer`·필드 수·정답 자체 | **A급 1건 이상이면 해당 회차 전 문항 재감사** |
| **B급** | 순수 표시 서식 — 줄바꿈·정렬·클래스·공백 | 수정 후 기록만 |

> 감사는 표본 검사이므로 완전 보증이 아니다. 운영 중 "정답 이의 제기" 버튼이 상시 신고 경로다.

### 판정 기입 규칙

- `판정` — `일치` / `불일치` / `판독불가` 중 하나.
- `등급` — 불일치일 때만 `A` 또는 `B`. 일치면 `-`.
- `근거` — 무엇을 어디서 보고 그렇게 판단했는지(이미지 파일명, page.txt 줄 번호 등).
  "확인함" 같은 서술은 근거가 아니다.

## B급 수정 내역 (2건 — 둘 다 `bodyHtml` 의 표 캡션 문제)

두 건 모두 `bodyText` 는 이미 옳았고 `bodyHtml` 만 어긋나 있었다. 표 셀 **값**은 하나도 건드리지 않았고

### 2024-1#13 — 머리행 접두사 → 캡션

`img01.png` 의 머리행은 `A|B|C` 와 `C|D|E` 이고, 표 이름 R1/R2 는 표 **위에 붙은 캡션**이다.

- **before**: `<tr><th>R1.A</th><th>R1.B</th><th>R1.C</th></tr>` / `<tr><th>R2.C</th><th>R2.D</th><th>R2.E</th></tr>`
- **after**: `<div class="desc-box"><b>R1</b></div>` + `<tr><th>A</th><th>B</th><th>C</th></tr>`,
  `<div class="desc-box"><b>R2</b></div>` + `<tr><th>C</th><th>D</th><th>E</th></tr>`

캡션 표기는 2026-2#13·2023-3#6 에서 이미 쓰는 `<b>` 라벨 관용구를 그대로 따랐다.

## 감사자 메모 (수정 대상 아님)

1. **#10 코드의 원문 오타를 보존** — 원본에 `this y=y;`(점 누락), `class Child extend Parent`(extends 아님),
   `class Child` 앞 폭 없는 공백(U+200B) 이 있고 JSON 이 앞의 두 개를 그대로 보존했다.
   이 문항은 **실행 순서**를 묻는 것이라 컴파일 가능 여부가 답에 영향을 주지 않고, 응시자가 실제로 본
   화면을 재현하는 쪽이 옳다고 판단했다. (`#8`·`#10` 같은 "코드를 고쳐야 답이 나오는" 문항이 아니다.)
2. **#19 의 `% 25` 를 보존** — 대문자 분기만 `%25` 이고 소문자는 `%26`, 숫자는 `%10` 이다.
   원문 그대로이며, 여기를 `%26` 으로 "고쳤다면" 출력이 달라질 수 있는 자리라 손대지 않은 것이 옳다.
   이번 입력 "It is 8" 에서는 대문자가 `I` 하나뿐이고 (8+5)%25 = 13 이라 %26 이어도 결과는 같지만,
   판단 근거로 남긴다.
3. **#5 에 validator 를 쓰지 않은 것** — 2026-2#10 은 같은 유형인데 `ip-in-subnet` validator 를 쓴다.
   차이는 **이 문항에는 보기 6개가 닫힌 집합으로 주어진다**는 점이다. validator 를 쓰면 보기에 없는
   임의 호스트 주소까지 정답이 되어 문항 취지가 깨지므로, RESTORE_GUIDE 의 "열거 가능하면 열거 우선"
   원칙대로 `accept` 열거가 맞다. 두 회차의 처리가 다른 것은 **의도된 차이**다.
4. **발문 다듬기 3건** — #3 "응집도와 관련해서" → "응집도와 관련된 문제이다", #5 "라우터을" → "라우터를",
   #9 "페이지 순서를 참고하여" → "페이지 참조 순서이다 … 각각 작성하시오". 내용·정답 불변.
   #13 `prompt` 에 붙은 "(결과 테이블의 행을 위에서부터 순서대로 작성)" 은 2필드 순서를 입력창에
   대응시키기 위한 안내이고, 원문 `더보기` 가 이미 a·b 순으로 답을 준다.
