## 감사 방법 (읽고 시작할 것)

1. **JSON 을 먼저 보지 않는다.** `sourceImages` 의 이미지와 `data/raw/<회차>/` 원본
   (`page.txt`, `article.html`, `imgNN`)만 보고 **독립적으로 재판독**한다.
2. 재판독이 끝난 뒤에야 `data/rounds/<회차>.json` 을 열어 대조한다.
3. 문항마다 아래 **판정 / 등급 / 근거** 3칸을 채운다. 빈칸이 남으면 감사 미완료다.

### 불일치 등급 (RESTORE_GUIDE "감사 규약")

| 등급 | 정의 | 조치 |
|---|---|---|
| **A급** | 채점 영향 또는 지문 내용 변경 — `bodyHtml`/`bodyText` 의 수치·식별자·코드 리터럴·표 셀 값, `accept`·`validator`·`sampleAnswer`·필드 수·정답 자체 | **A급 1건 이상이면 해당 회차 전 문항 재감사** |
| **B급** | 순수 표시 서식 — 줄바꿈·정렬·클래스·공백 | 수정 후 기록만 |

> 감사는 표본 검사이므로 완전 보증이 아니다. 운영 중 "정답 이의 제기" 버튼이 상시 신고 경로다.

### 판정 기입 규칙

- `판정` — `일치` / `불일치` / `판독불가` 중 하나.
- `등급` — 불일치일 때만 `A` 또는 `B`. 일치면 `-`.
- `근거` — 무엇을 어디서 보고 그렇게 판단했는지(이미지 파일명, page.txt 줄 번호 등).
  "확인함" 같은 서술은 근거가 아니다.

## #11 RIP 판정 시험 기록 (지시 항목)

img01.png 간선: A-B 2, B-D 2, A-D 1, D-C 2, C-E 1, C-F 5, E-F 2.
RIP 은 홉 수를 메트릭으로 쓰므로 A→D→C→F(3홉)가 정답이고, 가중치 합이 더 작은 A→D→C→E→F(합 6, 4홉)는 오답이다.

| 기대 | 입력 | 결과 |
|---|---|---|
| PASS | `A → D → C → F` / `A→D→C→F` / `A->D->C->F` / `A-D-C-F` / `ADCF` / `A,D,C,F` / `A D C F` / `a → d → c → f` | 전부 PASS |
| FAIL | `A → D → C → E → F` / `A-D-C-E-F` / `ADCEF` (가중치 최단, 4홉) | 전부 FAIL |
| FAIL | `A → B → D → C → F` (4홉) / `A → B → D → C → E → F` (5홉) / `F → C → D → A` (역순) | 전부 FAIL |

## 닫힌 보기 accept 오염 점검 (신설 세칙)

`accept` 에 같은 보기의 경쟁 항목이 섞였는지 전 문항 기계 점검했다. **위반 0건.**

- 다필드 문항은 #3·#4·#8 뿐이고 셋 다 닫힌 보기 목록이 없는 개방형(SQL 키워드 / 숫자 / 교환방식 용어)이다.
  세 문항 모두 필드 간 `accept` 교집합이 공집합임을 정규화 후 대조로 확인했다.
- 기호 보기를 가진 #9(ㄱ~ㅅ 7항목)는 단일 필드이며 `accept` 가 정답 ㅂ 의 표기 변형만 담는다 —
  경쟁 항목(기능적·우연적·통신적·절차적·시간적·논리적)은 하나도 인정되지 않는다.
- #10 역시 단일 필드로 Iterator 표기 변형만 담고, 보기의 다른 패턴명(Singleton·Adapter·Visitor 등)은 인정되지 않는다.
