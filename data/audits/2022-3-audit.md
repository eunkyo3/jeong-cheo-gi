## 감사 방법 (읽고 시작할 것)

1. **JSON 을 먼저 보지 않는다.** `sourceImages` 의 이미지와 `data/raw/<회차>/` 원본
   (`page.txt`, `article.html`, `imgNN`)만 보고 **독립적으로 재판독**한다.
2. 재판독이 끝난 뒤에야 `data/rounds/<회차>.json` 을 열어 대조한다.
3. 문항마다 아래 **판정 / 등급 / 근거** 3칸을 채운다. 빈칸이 남으면 감사 미완료다.

### 불일치 등급 (RESTORE_GUIDE "감사 규약")

| 등급 | 정의 | 조치 |
|---|---|---|
| **A급** | 채점 영향 또는 지문 내용 변경 — `bodyHtml`/`bodyText` 의 수치·식별자·코드 리터럴·표 셀 값, `accept`·`validator`·`sampleAnswer`·필드 수·정답 자체 | **A급 1건 이상이면 해당 회차 전 문항 재감사** |
| **B급** | 순수 표시 서식 — 줄바꿈·정렬·클래스·공백 | 수정 후 기록만 |

> 감사는 표본 검사이므로 완전 보증이 아니다. 운영 중 "정답 이의 제기" 버튼이 상시 신고 경로다.

### 판정 기입 규칙

- `판정` — `일치` / `불일치` / `판독불가` 중 하나.
- `등급` — 불일치일 때만 `A` 또는 `B`. 일치면 `-`.
- `근거` — 무엇을 어디서 보고 그렇게 판단했는지(이미지 파일명, page.txt 줄 번호 등).
  "확인함" 같은 서술은 근거가 아니다.

   RESTORE_GUIDE 의 `keepSpace` 권고는 `"C N N L R P Y T"` 같은 **문자열 답**의 공백 오인정을 막으려는
   것이다. #1 은 숫자 4개짜리 행(`1,1,3,2`), #9 는 숫자 리스트 리터럴이라 공백 유무가 의미를 바꾸지
   않고, 오히려 `default` 여야 `1, 1, 3, 2` 와 `1,1,3,2` 를 함께 인정할 수 있다. 규약의 "순수 숫자 답은
   default" 쪽에 가까워 그대로 두는 것이 맞다고 판단했다.
4. **#2 accept 의 기호와 `default` 정규화** — `-`, `|x|`, `><` 같은 기호 답이 후행 구두점 제거에
   잘려 빈 문자열이 되지 않는지 `server/grader.js` 를 직접 확인했다. 제거 대상 정규식은
   `/["'\`.,;:]+$/` 뿐이라 안전하다.
5. **발문 다듬기 (5건)** — #1 "field의 경우 … 출력되므로" → "field의 2차원 배열이 예시처럼 출력되는 것을
   참고하여 … 각 행별로", #5 "아래 코드에 대한 출력 값을" → 실제 내용(서브네팅)에 맞게 재작성,
   #7 "아래 데이터 명령어를 적용할 경우" → "SQL 명령어를 순서대로 적용할 경우 (1), (2)의 출력값을 각각",
   #11 "형상 관리 항목을" → "형상 관리 도구에 해당하는 항목을", #12 "튜플의 수는?" → "튜플의 수를 각각
   작성하시오". 내용·정답 불변이며, 다필드 문항은 입력창 개수를 발문이 알려 주는 편이 필요하다.
   특히 **#5 는 원본 발문("아래 코드에 대한 출력 값을 작성하시오")이 5번이 아니라 4번 문항의 발문을
   복사한 것으로 보이는 명백한 오류**라 지문 내용(서브네팅)에 맞춘 것이 옳다.
6. **#6 의 보기 부재 안내** — 원본에 "(기호식 보기가 있습니다. ex: …)" 라고만 적혀 있고 실제 보기
   목록이 없다. JSON 이 `hint` 로 이 사실을 밝히고 직접 작성 형태로 낸 것은 정직한 처리다.
7. **#18 의 "임의 작성" 안내 보존** — 원본의 "(아래 그래프 기호는 정확히 기억이 나지 않아 임의로
   작성한 것이니 참고만 해주세요.)" 를 `hint` 로 옮겼다. 이미지 자체의 신뢰도 한계를 사용자에게
   그대로 전달하므로 유지가 맞다.
